# P4 实施记录：MongoDB 退役与普通聊天数据迁移

版本：2026-11-19。范围：`docs/剩余工作量清单.md` §5 P4 明细。

---

## 1. 一句话结论

普通聊天的 `ai_conversation` / `ai_message` 从 MongoDB 整体迁到 MySQL（复用 P3 已建的两张表），删除了全部 Mongo Repository、`@Document` 实体、`MongoConfig` 与 `spring-boot-starter-data-mongodb` 依赖；应用启动**不再连接 Mongo**。顺带把普通聊天的模型凭据从 `ai_properties` 表的旧密钥统一到服务端 `ai-meeting.llm.*`（修复了普通聊天 401），并补齐消息 `model_name` 与会话 `user_id` 归属。`mvn test` 60 项全绿，真实 DeepSeek 普通聊天 SSE 全链路闭环通过。

## 2. 数据迁移范围

因 P0 已确认 Mongo 中业务数据为 0（4 会话 / 4 题 / 2 聊天，均属同一用户的 2026-07 测试数据），本阶段命中计划 6.1「无真实使用数据」分支，采用**空库初始化 + 抽样验证 + 保留旧卷**，不做双写对账：

| 集合 | 目标表 | 处置 |
| --- | --- | --- |
| `ai_conversation` | MySQL `ai_conversation` | 实体 `@Document` → `@TableName`，`id` String → Long 自增，新增 `user_id` / `version` / `active_request_id` |
| `ai_message` | MySQL `ai_message` | 实体 `@Document` → `@TableName`，`id` String → Long 自增，新增 `request_id` / `status` / `model_name` |

旧 Mongo 数据卷 `ai-meeting-main_mongo-data` 与 `ai-meeting-mongo` 容器**原样保留**，未做任何 drop / 清理。

## 4. 普通聊天模型凭据统一（401 修复）

**现象**：普通聊天调用 DeepSeek 报 `401 Unauthorized from POST https://api.deepseek.com/chat/completions`，但消息已正确落 MySQL。

**根因**：`UniversalAiChatHandler.createChatClient` 一直从 `ai_properties` 表读 `api_key`，而该表 id=3/4 的旧密钥（`sk-0178a585a...`）与真实密钥（`application-local.yaml` 的 `ai-meeting.llm.api-key`）不一致。这是 P2 遗留的「普通聊天模型来源与面试链路统一配置并存」问题，非 P4 引入。

**修复**：`UniversalAiChatHandler` 注入 `LlmProperties`，当 `ai_type` 为 `deepseek` 时，`baseUrl`/`apiKey`/`model` 固定取 `ai-meeting.llm.*`，不再读 `ai_properties` 表。与计划 §9「服务端固定/校验 DeepSeek 配置」一致，同时兑现 P2 记录中「P4/P6 统一」的遗留项。
