### 3.1 初始失败的两层原因

**第一层：测试代码编译不过（11 处构造器签名不匹配）**

| 测试文件 | 错误处数 |
| --- | --- |
| `interview/flow/session/InterviewSessionFacadeConsistencyTest` | 4 |
| `interview/application/InterviewSessionFacadeTest` | 3 |
| `interview/flow/session/InterviewSessionFacadePressureTest` | 2 |
| `interview/service/impl/InterviewRecordServiceImplTest` | 1 |
| `interview/flow/report/InterviewRecordFinalizeConcurrencyTest` | 1 |

根因：`InterviewSessionFacade` 新增 `runtimeSnapshotService`、`runtimeRehydrateService` 两个依赖（现为 8 个），`InterviewRecordServiceImpl` 同样新增这两个（现为 7 个），测试仍按旧签名构造。

**第二层：即使编译通过，测试也一个都跑不了**

`admin/pom.xml` 的 surefire/failsafe 配了 `<argLine>@{argLine} -javaagent:...mockito-core...jar</argLine>`，但项目**没有引入 jacoco 等覆盖率插件**，`@{argLine}` 这个延迟占位符无人赋值，导致 surefire fork 启动失败（`Error occurred in starting fork`）。表现是 `Tests run: 0` + BUILD FAILURE——看起来像"没有测试"，其实是 JVM 根本没起来。

### 3.2 修复内容

| 文件 | 改动 | 说明 |
| --- | --- | --- |
| `admin/pom.xml` | 新增 `<argLine></argLine>` 属性（空值） | 让 `@{argLine}` 可解析，同时保留后续接入 jacoco 的注入点 |
| 5 个测试文件 | 构造器补 `runtimeSnapshotService` / `runtimeRehydrateService` 两个 mock | 共 11 处，按主代码当前字段顺序追加在末尾 |
| `InterviewRecordServiceImplTest` | `selectOne` 桩由 3 个返回值改为 2 个；InOrder 断言改用 `calls(1)` | 见下 |
| `XunfeiAudioServiceAssemblerTest` | `noPgsPartial_ShouldReplaceCurrentLiveSnapshot` 标记 `@Disabled` | 见 R12 |

`InterviewRecordServiceImplTest` 的两处断言修正细节：

- 现实现里 `saveInterviewRecordFromRedis` 会先查一次会话判断是否已结束，再调用两次 `saveInterviewRecord`，每次内部各查一次归属。测试原来按"3 次 selectOne"配置桩数据，但实际只有 2 次查询，第二次仍返回 `null`，于是又走了一次 `insert`（实际序列 `selectOne→insert→selectOne→insert`，期望是 `...→updateById`）。已把桩改为 `thenReturn(null, existingRecord)`。
- 序列断言最初仍失败，原因是 **`inOrder.verify(mock)` 默认等价 `times(1)`**：`requireOwnedSession` 被调用 3 次，第一次断言就报 `Wanted 1 time but was 3 times`。InOrder 中同一方法多次调用必须用 `calls(1)` 逐个消耗。

### 5.6 R11 修复记录（未登录语义）

**问题**：未登录访问受保护接口返回 `HTTP 200` + `code=B000001 系统执行出错`，且 `NotLoginException` 以 ERROR 级打印完整堆栈。

**根因**：`NotLoginException` 没有任何专门处理器，落到 `GlobalExceptionHandler#defaultErrorHandler(Throwable)`，被统一包装成"系统执行出错"；同时该方法以 `log.error(..., throwable)` 输出堆栈。前端 `request.ts` 只认 HTTP 状态和 `A`/`B` 业务码，于是把"该重新登录"误判为"服务崩溃"，`userSlice` 也不会清理本地 token。

**改动**：

| 文件 | 改动 |
| --- | --- |
| `common/convention/errorcode/BaseErrorCode.java` | 新增 `UNAUTHORIZED_ERROR("A000401")`、`FORBIDDEN_ERROR("A000403")` |
| `common/web/GlobalExceptionHandler.java` | 新增 `NotLoginException` → HTTP 401 + `A000401`；`NotPermissionException`/`NotRoleException` → HTTP 403 + `A000403`；两者均 `WARN` 单行、不打堆栈 |
| `GlobalExceptionHandlerTest.java` | 新增 2 个用例，断言状态码与业务码 |
| 前端 `src/lib/request.ts` | `mapBusinessCode` 补 `A000401`/`A000403` 映射（HTTP 状态已覆盖，此处为二次包装兜底） |

**实测**（应用真实启动后 curl）：

```
GET /api/ai-meeting/v1/interview/conversations          → HTTP 401  {"code":"A000401","message":"未登录或登录状态已失效","success":false}
同上，带 Authorization: Bearer fake-token-123        → HTTP 401  （type=-2 token 无效）
```

日志侧对照：`WARN ... [unauthorized] loginType=login type=-1`（单行，无堆栈），修复前是 ERROR + 完整堆栈。

**回归**：测试套件从 91 项增至 **93 项，0 失败，1 跳过（R12）**。

**未做的事**：其余业务失败仍是 `200 + 业务码`（如参数校验 `A000001`）。把全部失败统一为 4xx/5xx 属于计划 §9 的契约改造，需与前端、Vue 新前端一起定，不在本次范围。
