### 3.1 存储现状（与后文迁移量的前提，必须以此为准）

以下为 2026-11-18 对源码和 `admin/src/main/resources/sql/table.sql` 的实际核对结果，用以修正"Redis 权威 + MySQL 摘要对账"的粗略印象：

| 数据 | 当前实际介质 | 说明 |
| --- | --- | --- |
| `interview_session` | **MongoDB** `@Document` | 面试会话主记录 |
| `interview_question` | **MongoDB** `@Document` | 题目与题序 |
| `interview_session` 热/冷快照、轮次归档 | **MongoDB** | `InterviewSessionRuntimeHotSnapshot`、`InterviewSessionRuntimeColdSnapshot`、`InterviewSessionTurnArchive` |
| `ai_conversation` / `ai_message` | **MongoDB** `@Document` | 普通聊天会话与消息 |
| `agent_conversation` / `agent_message` | **MongoDB** `@Document` | 通用 Agent，面试历史也复用其 DTO |
| 面试摘要、简历分等 | MySQL `interview_record` | 面试相关**唯一**已存在的 MySQL 表 |

MySQL 现有表只有：`admin_permission`、`agent_file_asset`、`agent_properties`、`agent_tag`、`ai_message_media`、`ai_properties`、`interview_record`、`t_user`。

**结论：第 6 节"能扩展已有表就扩展"仅对 `interview_record` 成立。会话、题目、回答提交、聊天会话/消息在 MySQL 中没有任何对应表，必须全部新建。** 这不是"收敛"，而是把 Mongo 上的全部核心业务数据搬到新建的 MySQL 表，量级应按"新建 5~6 张表 + 全量数据迁移 + 双写/切换"估算，而不是按"加几列"估算。第 4.1 节"读取 MySQL 会话、当前题和正式提交记录"在改造完成前是不成立的描述。

## 4. 目标架构与简化边界

```text
Vue 3 Web
  ├─ 账号、首页、历史
  ├─ 文字面试：材料 → 当前题 → 评分/追问 → 复盘
  └─ DeepSeek 普通聊天（SSE）
          ↓
Spring Boot / Java
  ├─ 鉴权、归属校验、限流、输入校验
  ├─ 面试服务 + 状态机 + 必要的 LiteFlow 追问规则
  ├─ 本地材料提取 + Qwen 视觉适配器
  ├─ DeepSeek 文本适配器
  └─ MySQL 仓储 + 少量 Redis 协调/缓存
          ↓
MySQL：唯一正式业务数据来源
Redis：会话锁、接口限流、现有登录所需状态、可丢弃查询缓存
```

不引入新的工作流平台、消息中间件、向量库、语义缓存或自研通用分布式任务框架。保留现有状态机和有价值的 LiteFlow 规则，不把每一个普通服务调用都包装成流程节点。架构以单实例正常运行、数据库可保护关键写入为基础，不声称已经完成高可用或压测。

## 5. 材料解析与模型调用

### 5.1 适配器与配置

先检查现有 Spring AI/OpenAI 兼容客户端能否复用，不同时保留多套重复 SDK。文本和视觉使用独立配置对象及客户端，防止 Base URL、Key、模型参数互相覆盖。

建议配置项：`TEXT_BASE_URL`、`TEXT_API_KEY`、`TEXT_MODEL`、`VISION_BASE_URL`、`VISION_API_KEY`、`VISION_MODEL`，以及独立超时、上下文和输出预算。这里只规定配置职责，不提供假 URL 或真实密钥。

默认文本模型是 `deepseek-chat`，视觉模型按用户指定 `qwen3.8-omni-flash`。该视觉标识、平台是否提供、API 权限、流式约束及参数必须通过实际供应商文档或最小探测核对；不得静默改成其他模型。不可用时明确报告阻塞原因，保持配置化，不用 mock 冒充成功。

测试默认使用显式注入的 mock。真实调用与离线测试分开，真实探测不能伪造准确率、费用或耗时结论。

### 5.2 文件支持与解析

用户接受保留现有格式并按需视觉处理。**现状必须说准确：前端 `resumeAccept` 只有 `.pdf`（`src/lib/constants.ts`），后端上传参数名为 `resumePdf`，即当前实际只支持 PDF。** 因此目标支持 PDF、DOCX、JPG/JPEG、PNG、WEBP 中，后四类是**净新增能力**，不是"保留"，需按新增功能估算解析器、校验、前端提示和测试成本。每种格式都必须有后端验证和前端一致提示，不只改 `accept` 属性。

- 初始文件上限 10 MiB，可配置；PDF 初始最多 20 页；文档展开、渲染像素、图片数量和送模文字长度均设上限。
- 文字 PDF 优先本地提取；DOCX 提取段落、表格和文本框，按顺序去重处理兼容分支。
- 图片、扫描页或提取质量不足的页交给 Qwen。混合 PDF 按页识别，避免部分扫描页遗漏。
- DOCX 的重要内嵌图片按需要交给视觉模型；不要把装饰图全部送模。
- 不把“文字提取为空”直接等同于“简历没有内容”；解析后验证实质内容，失败给出可重试/需更换材料的明确原因。
- 有证据的技能、项目、经历与推测分开；材料是待处理数据，不能改变系统指令。
- 当前没有确认新增 JD 上传能力；若现有 Java 实现支持则保留，若不支持不要因为另一 Python 项目有 JD 就自动扩展本次范围。解析结构可预留可选岗位文本，但不因此新增整套产品流程。
- 原文件仅用于临时提取/预览；默认不新增长期原件存储。临时文件成功或失败后都清理。旧原件链接迁移只保留来源信息，不默认重新下载到长期目录。若确认现有业务必须长期下载原件，再单列存储与删除策略。

### 5.3 Java 内的提示词和输出契约

在后端资源目录维护带版本号的材料整理、出题、评分、追问提示词与 JSON Schema/DTO。可参考旧 `resources/workflow/` 导出文件提取业务要求，不把这些 YAML 当成可直接运行的新工作流。

- 出题：题量、顺序、类别、题干、评分要点；代码验证题量和重复。评分要点不下发给未作答页面。
- 评分：0–100 总分、反馈、缺失要点、是否建议追问及依据。模型建议只是输入，代码决定是否追问。
- 追问：围绕当前回答缺口生成一个可回答的问题。**现有代码的默认值与本计划不同，必须先定死**：`InterviewAnswerPipeline`（约 485 行）在 `maxFollowUp` 为空时取 `2`，即当前实现默认每主问题最多 2 次追问；本节原写"默认 1 次"。实施时二选一并写入配置与文档，不得两处各说一套。在数值确定前，以代码现状 `2` 为准做回归基线。
- 输出解析必须校验类型、范围、非空内容、长度和关联关系；一次结构修复仍失败则记录失败，不伪造成功结果。
- 主问题和追问分别记录评分；整体面试分默认只统计已成功评分的主问题，追问评分单独展示，防止追问次数改变主问题权重。
- 不为了迎合前端填充默认 0 分；缺失分数是 null，跳过和失败单列。
- 材料、问题、答案、模型输出都是不可信数据。模型不能决定 SQL、权限、题序或执行外部操作。

## 6. MySQL 数据模型与迁移

以下是逻辑表建议。实现前检查现有 `resources/sql/`、Mapper 和表结构；**已核对：MySQL 中仅有 `interview_record` 一张面试相关表，可扩展复用的是它；会话、材料、题目、回答提交、聊天会话/消息均无对应表，必须新建，详见 3.1。** 除 `interview_record` 外不要预期"能扩就扩"，并避免同一实体既新建表又保留旧摘要造成双源。新增列、索引、约束必须提供版本化 SQL 或项目已有迁移机制；不要只改 Java 实体，也不要无必要引入迁移框架。

| 逻辑表 | 关键字段/职责 |
| --- | --- |
| 面试会话 | sessionId、userId、status、currentQuestionId、version、operationEpoch、activeSubmissionId、起止时间 |
| 面试材料 | sessionId、解析结构 JSON、解析状态、解析版本、模型/提示词版本、简历分数及反馈、错误信息 |
| 面试准备任务 | sessionId、prepareRequestId、阶段、状态、attemptToken、开始/完成时间、错误信息；可合并到会话/材料表，不强制另建通用任务平台 |
| 面试题目 | questionId、sessionId、kind、mainIndex、followUpIndex、parentId、题干、类别、评分要点 JSON |
| 回答提交 | submissionId、sessionId、questionId、requestId、inputHash、原答案/skip、状态、attemptToken、已完成阶段、评分 JSON、响应快照、错误、时间 |
| 普通聊天会话 | conversationId、userId、标题、状态、version、活动请求、时间 |
| 普通聊天消息/轮次 | conversationId、turnId/requestId、顺序、角色、正文、状态、模型信息、错误与时间；以唯一约束保证同轮消息不重复 |
| 面试记录/报告 | 尽量沿用 interview_record，最终摘要和报告版本；不要与实时回答重复计算后产生无法解释的分差 |

索引与约束至少覆盖：会话归属及时间排序、题目顺序唯一、`(sessionId, requestId)` 唯一、每题至多一个有效提交、聊天同轮角色唯一、必要外键或等价一致性校验。每题可采用单提交行重试，失败更新同一行；需要保留多次尝试时将尝试日志与有效提交拆开，不能用每次新建有效行绕过约束。

长文本用 TEXT/LONGTEXT，结构字段可用 JSON；真正参与检索、排序和约束的字段独立成列。确认 MySQL 版本、字符集、时间语义和 JSON 支持，不把整个业务塞进一个 JSON。

### 6.1 历史数据迁移

先盘点集合条数、会话归属、最新活动时间、文件来源和有效性；离线盘点不改变旧库。生成数据库备份和迁移报告。凭据不写报告。

- 普通 AI 会话/消息 → MySQL 聊天表。
- 面试会话、题库、快照与归档 → 会话、材料、题目、回答和报告。
- 按 sessionId、requestId 和题号对账，优先已提交的正式结果；时间戳最新不必然等于业务有效。
- 来源冲突、缺少用户归属或证据不足时隔离记录，输出原因；不能猜测回答或把会话恢复到可写。
- 通用 Agent 历史不导入普通聊天作为新功能；原库备份保留，可提供离线归档导出，面试依赖的历史记录另按面试数据识别迁移。
- 神态/语音旧字段可保留在离线旧备份中，目标业务不读取、不计算、不显示。
- 迁移脚本提供 dry-run、稳定来源 ID 映射、幂等重跑、计数核对和按会话抽样；不要每跑一次增加一批重复消息。

没有发现真实使用数据时，允许使用新测试库验证并切换配置；不得自动 drop 旧库。存在真实使用数据时，采用短维护窗口停止旧写入、备份、迁移、核对、切换，避免建设双库双写同步。切换后发生新写入，不能仅改配置回旧库：必须先冻结新写入并导出/对账增量，防止回滚丢数据。

## 7. 并发、幂等与失败恢复

### 7.1 提交处理

用户每次新提交生成 requestId；只有同次重试复用。输入指纹由题目 ID、提交类型、原回答及必要上下文版本确定，不能做语义相似匹配。相同 requestId 不同输入返回请求冲突。

1. 校验登录和会话归属，校验请求与限流。
2. 查询正式提交：SUCCEEDED 返回已存结果；PROCESSING 返回可查询的处理中状态。
3. 新提交/允许重试获取 `sessionId` 粒度 Redis 会话锁；结束、显式恢复、准备结果写入也遵守相同互斥规则。
4. 短事务重新检查会话与题号，登记/领取提交，更新处理代次和会话操作代次，事务结束。
5. 不持有数据库事务调用模型。Redis 锁默认看门狗续期；异步切线程不能错误释放非所属线程的 Redisson 锁，结束路径统一清理。
6. 完成短事务通过会话状态、题号、版本和 attemptToken/operationEpoch 条件检查，原子写评分、追问题、提交终态、下一题和可回放响应。
7. 成功提交后失效必要查询缓存，释放会话锁。

数据库的条件更新负责拒绝旧执行者迟到结果。不能只依赖 Redis 锁仍有效或只在内存里比较版本。不同会话可并发，同一会话同一时刻只接受一项改变流程的操作。

成功响应回放仅表示“同次请求再返回原结果”，不是通用 AI 语义结果复用。旧响应的 nextQuestion 是历史事实，前端发现版本落后时同步当前状态，不能倒退到旧题。

### 7.2 状态与失败

会话建议：DRAFT、PREPARING、PREPARATION_FAILED、IN_PROGRESS、FINISHED、CANCELLED。提交建议：PENDING、PROCESSING、SUCCEEDED、FAILED。以真实状态表达，不随意把处理中写成失败。

- 解析/出题失败：记录失败阶段；已有解析结果则重试出题不重复解析。
- 评分失败：答案保留，题序不推进，无有效分数；用户用原 requestId 重试。
- 评分已完成而追问网络或模型失败：保存阶段结果，默认跳过追问并记录原因，继续下一主问题；数据库故障不能伪装成可跳过的追问失败。
- 进程中断：将孤儿处理记录核对为需重试；首次恢复或受控启动核对时按期限和代次处理。期限必须覆盖配置中的最大调用预算，不能看到 PROCESSING 就抢占活跃请求。
- 不建设自动跨节点接管/无限后台重投。重试领取更新代次，旧进程即使迟到也无法落库。
- 提交与结束竞争时，锁内返回明确 busy 或按已提交状态执行；不能让终态会话被旧模型结果重新打开。

### 7.3 普通聊天

普通聊天也需要按会话串行一轮回复，避免两条消息同时读取旧历史。请求 ID 与消息状态落 MySQL；读取最近 N 轮并控制 token 预算，不每次加载全部历史。

SSE 建议使用 `start`、`delta`、`done`、`error` 结构化事件和 requestId；分块传输与 UTF-8 解码正确处理。前端停止/断开时尽力取消上游调用，持久化中断状态。已完成同次重试返回/发送已保存正文，不能再次调用模型。不要为恢复 SSE 建立另一套 Redis Stream 协调框架。

### 7.4 Redis、线程池、限流的精简范围

- Redis 保留：现有鉴权所需数据、会话锁、基础用户/IP 限流、可选的短期列表缓存。
- 去掉：权威题序、权威累计分、问答正式历史、独立模型结果缓存、模型任务 meta/heartbeat/notification、多份请求去重集合和其补偿队列。
- 面试总分从 MySQL 成功评分聚合得到，之后不再维护 Redis 分数聚合 Lua。Lua 仅在确有必要的原子协调处保留；不可为了技术栈描述而保留代码。
- 保留一个有界 AI I/O 执行池及必要调度能力；普通聊天长连接也受全局并发预算约束。先核对调用关系，再移除无实际用途的 CPU/query 线程池，不擅自挪动无关业务任务。
- 并发额度是每实例额度，不代表集群总容量。默认保守配置，实际容量通过后续测试确定，不编造 QPS。
- 供应商调用、客户端与业务修复合计有明确调用预算；网络临时故障最多有限重试，结构错误最多一次修复，权限/配额/参数错误不自动反复重试。
- 超时表示本服务停止等待，不保证供应商停止计费；取消是尽力行为。不要承诺模型 exactly-once。

## 8. 评分与报告

原 `WeightedRadarComputationStrategy` 综合分权重是简历 25%、面试 55%、神态 20%。去掉神态后，默认将保留项归一化为简历 31.25%、面试 68.75%，仅当两项有效时计算。只有一项时显示该项分数及覆盖情况；两项都没有时 null。归一化数值已核对无误（0.25/0.80=31.25%，0.55/0.80=68.75%）。

该类还有两处必须一并处理，原计划未点明：

- 类中另有一组 `PROFESSIONAL_SKILLS_RESUME_WEIGHT 0.30` / `PROFESSIONAL_SKILLS_INTERVIEW_WEIGHT 0.70`，它**不是第二套综合分**，而是 `professionalSkills` 这个雷达轴的算法（简历 30% + 面试 70%）。这正是本节要禁止的"把同一简历分和面试分包装成多个独立能力轴"，应在删除雷达轴时一并删除。
- `defaultScore()` 把 `null` 分数写成 **0**，`calculateProfessionalSkills`/`calculateWeightedComposite` 在 `totalWeight<=0` 时也返回 0。这直接违反 5.3"不为了迎合前端填充默认 0 分；缺失分数是 null"。报告改造时必须区分"没作答/没评分"与"得了 0 分"，否则覆盖率统计会被污染。

产品优先突出面试分、简历分与题目表现；综合分是练习参考。沿用上述权重是默认实现决定，不声称它是经科学验证的能力指标。旧报告标注旧评分版本，不静默用新公式覆盖历史成绩。

- 移除神态、情绪、恐慌、严肃程度、仪态及其衍生评分。
- 不把同一简历分和面试分包装成多个独立能力雷达轴。新报告优先使用分类条形图、题目列表和缺失要点。
- 报告展示主问题总数、已完成/跳过/失败/未答、有效评分覆盖率、主问题均分、追问表现、分类表现、答案证据与建议。
- 建议从既有评分和缺失要点聚合生成；打开报告不再次调用模型。
- 提前结束生成部分报告，未答不计零分；失败不当作用户不会。
- 最终报告可按评分版本保存快照；未终态报告明确标记“进行中”。

## 9. API 契约和兼容策略

优先沿用 `/api/ai-meeting/v1` 前缀与现有登录体系，保留能复用的 Result 包装，但统一分页、错误字段和失败 HTTP 状态。现有接口业务错误可能在 200 响应中，应明确统一策略并同步新前端，不让各页面猜测失败。

| 能力 | 现有入口/目标处理 |
| --- | --- |
| 登录注册/当前身份 | 复用当前用户模块，实施时确认真实路由、token header 和过期行为 |
| 创建面试 | `POST /interview/sessions`，返回 sessionId/status/version |
| 面试列表 | 复用 `/interview/conversations`，统一分页 |
| 上传准备 | 复用 `POST /interview/sessions/{id}/interview-questions`；目标受理后返回 202 与准备任务状态，新前端适配 |
| 准备/会话进度 | 增补明确 GET 状态接口，返回解析/出题阶段；轮询成功、失败、退出时停止 |
| 当前题 | 保留 current-question，严格只读，不因 GET 推进题序 |
| 答题 | 主用 JSON 提交入口，含 questionId/题号、requestId、answer 或 skip、预期版本 |
| 提交状态 | 增补按 requestId 查询接口；只返回当前用户的提交 |
| 准备重试 | 增补受保护的显式重试入口，复用已解析材料 |
| 恢复 | 从 MySQL 正式状态读取；正常刷新无需执行破坏性恢复 |
| 结束 | 合并 finish/end 的内部实现，重复结束幂等 |
| 报告与记录 | 统一报告 DTO，历史接口按需要保留兼容适配 |
| 普通聊天 | 保留 `/ai/conversations` 和会话 chat SSE，服务端固定/校验 DeepSeek 配置 |
| 通用 Agent、神态、语音 | 新前端无入口；稳定切换后移除旧路由和依赖 |

`next-question` 旧接口若有推进副作用，改为兼容只读或废弃，不允许 GET 跳题。未答主问题和评分要点不通过通用题库接口提前暴露。

**已定的一条失败语义（2026-11-19）**：未登录/登录失效返回 **HTTP 401 + `A000401`**，角色权限不足返回 **HTTP 403 + `A000403`**，鉴权失败只记 WARN、不打堆栈。前端据 HTTP 状态即可判定"该重新登录"，不再从 `B000001 系统执行出错` 里猜。其余业务错误目前仍是 `200 + 业务码`，是否统一改为 4xx/5xx 在 P0 契约阶段一次性定，不逐接口零散改。

请求冲突/旧题/会话忙使用明确错误码（如 REQUEST_CONFLICT、STALE_QUESTION、SESSION_BUSY）；参数错误、权限失败、过载和模型不可用分别可识别。处理中建议 202，返回 requestId、查询地址或重试间隔；最终采用的 HTTP/Result 组合写入接口说明并测试。

登录 token 沿用现有方案，本次不顺带重构鉴权。所有新表读取写入都按 userId 归属；缓存键包含必要身份/会话，前端不发送可随意切换他人身份的 userId。模型密钥仅在后端环境，前端不包含供应商 Key 或 Secret。CORS 按明确来源配置，不照搬聊天 Controller 的通配符响应头。

## 10. Vue 前端重设计

### 10.1 技术栈与目录

Vue 3 + TypeScript + Vite + Vue Router + Pinia；请求层复用现有鉴权语义，使用一套 HTTP 客户端；SSE 使用支持 POST 和认证头的 fetch 流处理。无需为简单页面引入第二套远程状态框架。

可用一套 Vue 兼容基础组件库加设计 token 定制，建议 Element Plus；不要混用多套视觉组件库，也不要把旧 React/shadcn 代码直接改后缀。图表只在数据真实、维度独立时加入。

建议目录：`src/api`（DTO/请求）、`src/stores`（身份/轻量会话）、`src/views`、`src/components`、`src/composables`（轮询/SSE/提交恢复）、`src/styles`。文件名称和路由以页面职责命名，服务端数据是权威，不长期复制出第二套题序状态。

### 10.2 信息架构

1. 登录/注册：表单、错误提示、登录过期和回跳。
2. 工作台：继续最近面试、新建面试、最近记录；统计只展示后端真实数据。
3. 新建面试：简历拖拽/选择、格式与大小提示、已选文件、确认开始；没有已实现的岗位/JD能力就不展示可用假控件。
4. 准备页：解析/校验/出题进度、从服务端时间推导耗时、失败原因、重试出题/更换材料。
5. 面试工作台：当前题、进度、主问题/追问标记、文字答案、提交/跳过/结束、上一题反馈与文字构思板。
6. 面试记录：状态筛选、分页、继续/查看报告；不默认一次拉全部消息。
7. 复盘报告：覆盖率、面试分/简历分/综合分、分类表现、逐题原文/反馈/追问、薄弱点。
8. 普通聊天：会话列表、流式回复、新建/重命名/删除、停止生成、错误重试。

不保留：通用 Agent 列表/聊天、Agent flowId 管理、星火供应商切换、摄像头、语音按钮、播报按钮、神态雷达、假题库入口。已有账号管理若确实被使用则保留最小入口，不扩建后台管理平台。

### 10.3 布局与视觉规范

- 风格：中文学习工具，浅色底、清晰分区、少量蓝绿色强调；避免大面积营销渐变和过度装饰。
- 桌面：约 224px 侧栏，64px 顶栏；内容区最大约 1280px。面试采用主区题目/输入 + 右侧反馈/构思，普通聊天使用自己的会话侧栏。
- 移动端：导航抽屉，面试单列，反馈/构思可折叠；输入区不会被固定底栏遮挡；320px 起无横向溢出。
- token 初稿：背景 `#F6F8FB`、表面 `#FFFFFF`、正文 `#172033`、次要文字 `#526079`、主色 `#2458D3`、边框 `#DCE3EE`；成功/错误必须同时使用文字说明。最终校验正文对比度至少 4.5:1。
- 间距：4/8/12/16/24/32/48px；字体：12/14/16/20/24/32px；圆角：8/12/16px。
- 字体候选：系统中文字体 + Inter；Noto Sans SC + Inter；Source Han Sans + system-ui。默认系统栈，避免依赖外网字体才能使用。
- 核心组件：AppShell、SessionCard、MaterialUpload、PreparationProgress、QuestionPanel、AnswerComposer、EvaluationPanel、TextSketchpad、ReportSummary、QuestionReview、ChatMessage、ErrorNotice。

### 10.4 交互与可靠性

- 每页都有加载、空、错误、成功状态；模型处理中不可重复创建新提交，但能查询状态。
- 提交前将同次 requestId 与答案保存到按用户/会话隔离的 sessionStorage；同次重试复用，不同输入产生新请求。未发送草稿另存，不能覆盖处理中提交。
- 刷新后先同步服务器状态，再恢复待提交请求；已成功结果显示反馈，题序取最新会话版本。
- 准备和提交状态轮询单飞、有退避、可取消，终态停止。页面切换、组件销毁、退出登录后取消请求并忽略迟到响应。
- 普通聊天 SSE 正确处理拆包、多事件、最终持久化标识、断流、取消和登录过期；同会话一轮生成中禁用第二次发送。
- 提前结束需要说明未答题不计分；繁忙时显示可重试，不假装结束成功。
- 文字构思板按用户/会话隔离保存，保留手写提纲和插入答案功能，不保留转写缓冲区。
- Tab 可访问、按钮有可见 focus、表单有 label、图表有文字数据替代、状态变化有适当 aria 提示；动画尊重 reduced-motion。
- 默认没有摄像头/麦克风权限申请、音频预加载和隐藏的媒体轮询。
